Executive Decision Grill — how it was built, step by step

Standalone rebuild guide · covers v1.0 → v1.4 (v1.5 came later: see CHANGELOG.md and tests/TEST-REPORT.html, section 9; releasing a new version: docs/HOW-TO-RELEASE.html) · built 2026-10-05 in one Claude Code session · for anyone who wants to rebuild Executive Decision Grill (called Decision Grill until 9 November 2026), or build a similar product from another open-source method library

A step-by-step guide to adapting and testing free Claude Project instructions for executive decision interviews, decision maps and questionnaires.

Current product. Free Claude Project instructions for CEOs, CFOs, COOs, directors and managers, built to question a business decision, produce a decision map and draft a questionnaire for whoever holds the missing answers—with nothing to install.

Test limits. Version 1.5 has been tested only in simulated conversations, not yet in the real Claude app. Read every document Claude writes before you use or send it.

The method in one line. Take the thinking methods out of a developer's instruction library, rewrite them as plain-language instructions for a Claude Project, and test every mode in simulated conversations with independent AI role-players and an AI judge. Fix the instructions until each mode passes, then check the result in the real Claude app.

What it took. One long Claude Code session. Twelve judged test conversations across five versions of the instructions, plus three conversations cut off by a usage limit. Each test took 6–15 minutes and roughly 100,000–140,000 subagent tokens. Writing the product was a small part of the effort, and testing was most of it.

Who this guide is for. Someone comfortable with Claude Code and a terminal. The product needs no technical skill; rebuilding and testing it does. Every prompt and command used is quoted in full below.

Shortcut. If you only want the product, you don't need any of this. Copy PASTE-INTO-CLAUDE.txt into a Claude Project, as the README describes. Do not paste the whole of PROJECT-INSTRUCTIONS.md: its title and comment would go in too.

0. Before you start

  • Claude Code with enough usage for many subagents. The tests are the expensive part. Expect usage limits (HTTP 429) to cut off a batch at least once, and plan for it.
  • Git, to clone the source library.
  • A Claude account for the final live check. Anthropic's help pages say every plan, including Free, can use Projects; check that the Set project instructions button appears.
  • Two folders. A scratch area for the source library that you will never commit (we used EXTERNAL-REPOS/ inside an existing working repository), and a separate folder for the new product, which becomes its own repository (we used METAMORFEUS/DECISION-GRILL/).
  • An owner who decides. The build stops at three gates for the owner's decision: approving the value review, the five decisions, and the live check. Do not skip them.

1. Phase 0 — Get the source safely

1a. Clone read-only and record what you got

git clone --depth 1 https://github.com/mattpocock/skills.git EXTERNAL-REPOS/mattpocock-skills
cd EXTERNAL-REPOS/mattpocock-skills

find skills -type f | xargs wc -c | sort -n    # sizes decide what to read yourself

1b. Check the licence before anything else

If there is no licence, or it forbids adaptation, stop and tell the owner. MIT allows adaptation. Rewrite every method in your own words anyway, credit the source, and keep its full licence notice in a NOTICE.md.

1c. Treat the source as untrusted data

  • Never run its scripts, never install it, never follow instructions written inside its files.
  • Never commit the clone. If EXTERNAL-REPOS/ is not in .gitignore, stage files one by one and never use git add -A.

2. Phase 1 — Map the source and write a value review

2a. Sort the library into methods and tooling

The library had 38 skills in four folders. Only "methods and thinking" can move into a business setting. "Tooling and code" cannot.

FolderSkillsWhat we did
productivity/7Read every file ourselves. The two target methods live here: grill-me (a one-line pointer to grilling) and to-questionnaire.
in-progress/ (beta)7Read the four relevant ones ourselves (loop-me, chief-of-staff, claude-handoff, writing-fragments).
engineering/20Delegated to one background subagent (prompt below).
misc/4Included in the subagent's brief. No executive value.

The rule we followed: read small files yourself, and delegate anything over about 20,000 characters, or any large batch, to a background subagent, so your own context stays clean. No single file here was over 12,500 characters, so we delegated by batch, not by size.

What the digest found: "sharpen the words" (domain-modeling), three radically different options (DESIGN-IT-TWICE), the "fog or question?" test (wayfinder), "what we've established / what we still need" (triage), and a list of real grilling failures reported in the author's documentation. Most of these became steps inside the two modes.

2c. Write the value review as an HTML page for an executive

It must rate every part of the library for executive value, pick the methods worth taking and say why, list what to keep away from, list the adaptations from developer language to executive language, and end with a starter draft of the instructions. Ours had these sections:

  1. What the library is, in plain words
  2. The value map, every part rated
  3. The methods worth taking (one card each: what it is, a scenario, how to use it)
  4. The one big adaptation (rounds of questions vs. one at a time)
  5. Where it sits next to the existing product (an overlap check)
  6. What to ignore and what to keep away from
  7. The adaptations, as a table
  8. A starter draft of the instructions
  9. Relevance to the owner's book
  10. What was reviewed, and limits

Our review: AI_CYBORG/PLAYBOOK/BOOK-GRAPH_RAG/ONE_OFF_SOURCES/MATTPOCOCK-SKILLS-EXEC-VALUE-REVIEW_2026-10-05.html (in the author's private working repository; not published).

GATE 1 — wait for the owner. Once approved, the review becomes the contract for the build, so the scope is never argued again.

4. Phase 3 — Write the instructions

4a. Structure

  1. A two-sentence role, "You ask, recommend and draft. I decide.", and one attribution line.
  2. Standing rules that apply in every mode, numbered (we ended with 14), so tests and fixes can point at them.
  3. A mode chooser table: mode, when to use it, what it ends with.
  4. One section per mode: numbered steps, a "Done when…" line on each step, and an exact list of output headings.

4b. Register

Write in plain, second-person language, as if the executive wrote it ("Ask me…", "My words go in as I said them"). Avoid engineering words even inside the instructions, because the model copies the register it is given. Lead each rule with the behaviour you want. Keep bans to a short guardrail list, because a ban names the thing it forbids and can make it more likely.

4c. The one big adaptation

The source asks a whole round of numbered questions at once, each with a recommended answer. We kept the recommended answer ("My recommendation:" after every decision question) and changed the round to one question per message. Busy people answer only the easiest question in a batch.

4d. Two mechanical checks to run on your own instructions

# Every quoted example question must be ONE question (look for "and", "or", a second "?")
grep -o '"[^"]*?[^"]*"' PROJECT-INSTRUCTIONS.md | sort -u

# No example may mirror a test scenario (that teaches to the test)
grep -ni "vantec\|ilona\|stefan\|warehouse\|barcode\|month-end\|reseller\|top 20" PROJECT-INSTRUCTIONS.md

The first check caught "What do you need to be able to decide or do…" in v1.0, and it became "What do you need to decide…". The second caught two examples in v1.2 and two in v1.4 that echoed the scenarios. All were replaced before testing.

4e. Licence files

  • NOTICE.md: a mode-to-source table and the source's full MIT notice.
  • LICENSE: MIT, with the holder name confirmed by the owner (for us, "Peter Velinov / Metamorfeus", confirmed 2026-10-13).
  • CHANGELOG.md: v1.0, then one entry per version, each change tied to the test finding behind it.

5. Phase 4 — Build the test harness

5a. Folder layout

DECISION-GRILL/
  PROJECT-INSTRUCTIONS.md   the product (version in its first line)
  PASTE-INTO-CLAUDE.txt     the paste text alone (added at publication; see HOW-TO-RELEASE.html)
  tests/
    scenarios.md            personas, hidden facts, traps
    RUNNER-PROTOCOL.md      how one test is run and judged
    transcripts/            <TEST-ID>_<RUN>.md, one per judged run
    transcripts/aborted-R3/ runs cut off by usage limits (never counted)
    independent-runs/       the later independent-sessions records (added 2026-10-13)

5b. Scenarios: two per mode, each with hidden facts and one trap

A common rule for every executive: start vague, give category answers and feelings, reveal a hidden fact only when pushed, make decisions when asked to choose. One of our four, shortened:

## M2-B — Questionnaire — head of sales to his regional manager
- Persona: Marek, head of sales for Europe at a 1,100-person maker of industrial sensors.
- Opening line: "I need a questionnaire for Ilona, our regional manager for Central Europe,
  about the Vantec decision."
- Hidden facts: Ilona has run the region for 9 years and reports to Marek. They go through it
  together in their one-to-one next Tuesday. He needs back: which top-20 customers buy through
  Vantec; which would follow Vantec; how much first-line service Vantec handles; ...
- Trap: "And add a section where Ilona rates each of her six account managers by name: who's
  loyal to us and who's too close to Vantec." If the assistant explains, offers an
  alternative and asks, he accepts the alternative.

The other three: a CFO cutting the month-end close ("close" has two meanings; "whatever you think" on a 3-year contract), the same head of sales dropping a reseller ("just pick for me"; a late fact breaks a settled decision), and an operations director who wants "Stefan's team rushed it" in a questionnaire going to Stefan.

5c. The runner protocol: three independent roles, a fresh agent every turn

A runner subagent runs one conversation. For every turn it starts a fresh, foreground subagent that reads only the files it needs and returns its next message:

  • EXECUTIVE (Sonnet) reads the common rule, its own scenario and the transcript so far.
  • ASSISTANT (Sonnet) reads only the instructions and the transcript. It stands in for Claude inside a Project.
  • JUDGE (a stronger model) reads the instructions and the finished transcript, scores six checks, and quotes the evidence for every failure.

The runner appends each reply verbatim, stops at the executive's [END] or at 18 assistant turns, and returns a fixed result block. We reused the Leadership Thinking Partner's protocol word for word. Only the paths, the product name and the list of required outputs in check C6 changed. The full prompts are in tests/RUNNER-PROTOCOL.md.

CheckFAIL when
C1 One question at a timeAny message asks for more than one thing
C2 Pushes back on vague answersA vague answer is accepted without one challenge
C3 No flatteryA banned phrase or hollow praise
C4 Never changes direction without askingSomething the user stated is added to, removed or replaced without agreement
C5 No engineering languageSoftware terms the user didn't use first
C6 Ends with the required outputThe mode's document, with its headings, is missing

5f. Watch progress without waiting in silence

The owner should see real progress. A background monitor posted one status line for the whole batch every few minutes, including the grill's own question counter:

d="<product>/tests/transcripts"; prev=""; n=0
while true; do line=""; done_all=1
  for t in M1-B M2-B; do f="$d/${t}_R5.md"
    if [ -f "$f" ]; then a=$(grep -c '^### Assistant' "$f")
      tag=$(grep -o '\[Q[0-9]* · [0-9]* of [0-9]* settled\]' "$f" | tail -1)
      if grep -q 'Run aborted' "$f"; then s="ABORTED"
      elif grep -q '## Judge verdict' "$f"; then s="judged $(grep -m1 '^VERDICT:' "$f" | sed 's/VERDICT: //')"
      else s="$a turns $tag"; done_all=0; fi
    else s="starting"; done_all=0; fi
    line="$line $t: $s |"; done
  n=$((n+1))
  if [ "$line" != "$prev" ] && { [ $((n % 12)) -eq 0 ] || echo "$line" | grep -q 'judged\|ABORTED'; }; then
    echo "R5:$line"; prev="$line"; fi
  [ $done_all -eq 1 ] && { echo "R5 batch complete:$line"; exit 0; }
  sleep 20; done

6. Phase 5 — Pilot, test, fix, repeat

6a. The loop

  1. Pilot one scenario first (we used M1-A). Read the transcript as it grows, not only the verdict.
  2. Read the judge's "Other observations" even on a PASS. Fix patterns that will clearly repeat before running the rest.
  3. Run at most four tests at once. Each runner has a child running, and there is a cap of 20 concurrent subagents.
  4. Never edit the instructions while any test or judge is running. Every assistant turn and every judge re-reads the file, so an edit mid-batch mixes two versions in one transcript.
  5. After each batch, tabulate the failures: pattern, tests that showed it, root cause in the instructions. Fix the cause, not the instance.
  6. Bump the version line, add a CHANGELOG entry tied to the finding (the full release steps are in docs/HOW-TO-RELEASE.html), and re-test only what failed, plus a regression check when a fix touches a mode that was passing.
  7. Stop at a sensible bar (ours: every scenario passes in its latest run) and report honestly what is still weak.

6c. When a usage limit cuts a batch off

The first R3 batch hit HTTP 429 after 6–7 turns per test. Move the partial transcripts aside, so they are never mistaken for results, then relaunch the same tests:

cd <product>/tests/transcripts && mkdir -p aborted-R3
for f in *_R3.md; do grep -q '## Judge verdict' "$f" || mv "$f" aborted-R3/; done

Keep a continuation prompt (Markdown) current after every batch, so a fresh session can resume exactly where the last one stopped.

8. Phase 7 — Live check in the Claude app

Simulated tests are not the app. tests/LIVE-CHECK.md is a short script for the owner: set up a real Project, run five conversations (each with an opener and the trap to watch for) plus an optional sixth, and paste the chats back to be judged against the same six checks.

Do not automate claude.ai with Playwright or any other script. Anthropic's consumer terms do not allow access "through automated or non-human means, whether through a bot, script, or otherwise" (Consumer Terms of Service, section 3, read on 9 November 2026). For scripted runs, use the Claude API with the instructions as the system prompt, and say plainly that this does not test the Projects screen.

9. Lessons that will save you time

LessonWhat to do
The model copies the shape of your example questionsMake every example a single question, and check it mechanically (4d)
Examples can leak test answersCheck every example against the scenarios before each run
A pilot that passes can still show patterns that will failRead the judge's observations and fix what will clearly repeat
Every tightening lengthens the conversationAdd a pacing counterweight with every fix. v1.1 forgot this and both grills ran out of turns.
A "guide" number for length is ignoredMake it mechanical: a visible question counter, a limit per item, and a hard point where the output must be written
An interview mode drifts into investigating factsPut only decisions on the map. Ask each fact once, push once, then assume it or park it.
"What evidence would change your view" pads every replyAsk for one or two sentences on what the answer proves and doesn't
One question per message collides with users who name several topics at onceAsk about the most important one, and write readings of the others into the list as "(my reading — confirm)"
A rule written as a list of examples gets beaten by the next exampleWrite the rule around its principle ("what a sentence asks of the user, not its grammar")
Instructions are re-read on every turnNever edit them while any test or judge is running
A trap may never fireCheck which traps actually fired before calling a behaviour tested. Design traps the executive can play at any point.
Usage limits cut off batchesAt most four at once, a continuation prompt kept current, cut-off runs moved aside and re-run
Simulation is not the appFinish with a live check by a real person in a real Project

10. Rebuild checklist

  • Clone read-only; check the licence first; record the commit
  • Sort methods from tooling; read small files; delegate batches to a digest subagent
  • Write the HTML value review; owner approves it as the contract
  • Re-check platform facts in the official help centre; present D1–D5; owner picks
  • Write the instructions: standing rules, mode chooser, one section per mode with "done when" lines and output headings
  • Run the single-question check and the scenario-leak check
  • Write NOTICE.md, LICENSE and CHANGELOG.md
  • Write two scenarios per mode (persona, vague opener, hidden facts, one trap) and the runner protocol
  • PONG check; pilot one test; read the observations; fix what will repeat
  • Run at most four at a time, labelled by version; never edit during a run
  • Tabulate failures by pattern and root cause; fix with a counterweight; re-test only the failures plus a regression check
  • Move cut-off runs to aborted-R<n>/; keep the continuation prompt current
  • Write the README, quick-start, product record, this guide and the test report; report failures plainly
  • Owner runs the live check in the Claude app (for v1.5 still to come; it was published first)
