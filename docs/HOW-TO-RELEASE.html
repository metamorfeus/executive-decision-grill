Executive Decision Grill — how to release and maintain it

For the maintainer · written 10 November 2026 · instructions v1.5 · repository metamorfeus/executive-decision-grill · status at writing: prepared, not published

A maintainer guide to checking the free Claude Project instructions, preparing a new version and publishing only with Peter’s explicit approval.

Who this is for. Whoever looks after the product: checking that the published text is the tested one, releasing a new version, publishing, and taking it down again. You need Git Bash, Python 3 and the GitHub command-line tool gh, signed in as metamorfeus. Executives do not need this page.

Three habits keep it safe. Stage files by name, because the product folder holds a private archive/. Change the text you paste only together with a new version number and a changelog entry. And do not open the sealed test scenarios, which are kept for one final, untouched test.

1. The files that must agree

The product is one text. Several files repeat it or describe it, and they must say the same thing.

FileWhat it must match
PROJECT-INSTRUCTIONS.mdThe source. Its first line holds the version. The text you paste starts at the line "You are my decision partner. I am a senior leader" just below the comment, and runs to the end of the file.
PASTE-INTO-CLAUDE.txtByte for byte the same as that text. The home page copy button reads this file.
CHANGELOG.mdThe top entry for each version gives the date, the changes, the character count and the SHA-256 fingerprint of the text you paste.
.gitattributesMarks both files above, and tests/independent-runs/, as -text. Git on Windows would otherwise change their line endings and break the fingerprints.
Pages that name the versionREADME.md ("Current version"), the footers of index.html and the guides, docs/WHAT-WAS-BUILT.html, tests/TEST-REPORT.html and RELEASE-CHECKLIST.html.

For version 1.5 the text you paste is 22,793 characters, SHA-256 9a987f08eb138da683199d8cb2c5e831a800340bd91647e52db8201f141bc036.

2. Check the fingerprint

Run this before and after any batch of edits, and before every commit. Both lines must show the same fingerprint, and it must match the top entry in CHANGELOG.md.

cd "/c/OD/OneDrive - ADVANCED HARMONY ASSOCIATION/METAMORFEUS/DECISION-GRILL"
python - <<'EOF'
import hashlib
b = open("PROJECT-INSTRUCTIONS.md", "rb").read()
i = b.find(b"\nYou are my decision partner. I am a senior leader") + 1
print("body ", hashlib.sha256(b[i:]).hexdigest(), len(b[i:].decode("utf-8")))
print("paste", hashlib.sha256(open("PASTE-INTO-CLAUDE.txt", "rb").read()).hexdigest())
EOF

After publishing, check what GitHub actually serves:

curl -s https://raw.githubusercontent.com/metamorfeus/executive-decision-grill/main/PASTE-INTO-CLAUDE.txt | sha256sum
curl -s https://metamorfeus.github.io/executive-decision-grill/PASTE-INTO-CLAUDE.txt | sha256sum

3. Release a new version

Use these steps for any change to the text you paste, even a single word. Changes that touch only the guides need steps 1, 7, 8 and 9.

  1. Back up. Copy every file you will change into archive/before-v<N.M>_<date>/, keeping the folder layout. archive/ is never published.
  2. Edit the instructions. Change PROJECT-INSTRUCTIONS.md below its comment, and the version in its first line. Keep the file's line endings as LF.
  3. Regenerate the paste file. This copies the text you paste into PASTE-INTO-CLAUDE.txt and prints the new count and fingerprint: 
    python - <<'EOF'
import hashlib
b = open("PROJECT-INSTRUCTIONS.md", "rb").read()
i = b.find(b"\nYou are my decision partner. I am a senior leader") + 1
body = b[i:]
assert i > 0, "start line not found"
assert b"\r\n" not in body, "line endings must be LF"
assert not body.startswith(b"\xef\xbb\xbf"), "no byte-order mark"
open("PASTE-INTO-CLAUDE.txt", "wb").write(body)
print(len(body.decode("utf-8")), "characters, SHA-256", hashlib.sha256(body).hexdigest())
EOF
    If you change the first sentence of the instructions, also change the line the copy button checks for (FIRST in the script of index.html) and the start line in the scripts on this page.
  4. Test what changed. Re-run at least the tests that touch the changed rule, and the live check in the Claude app (tests/LIVE-CHECK-SHORT.md). Record the result, good or bad, in tests/TEST-REPORT.html. Run every test or script that could loop or use a lot of memory through the memory cap (python C:\Scripts\capped_run.py -- <command>).
  5. Write the changelog entry. Add it at the top of CHANGELOG.md: the version, the date, each change with the finding that caused it, the new character count and the full fingerprint.
  6. Update the pages. Find every place that still names the old version, count or fingerprint, and update it: 
    grep -rn -E "v?1\.5|22,793|9a987f08|about 23,000" --include=*.md --include=*.html . | grep -v "^./archive/"
    Keep the honest limits up to date in the README, the home page and the guide for executives: what was tested, on which version, and what was not.
  7. Check the published file set in a throwaway copy, never in the product folder itself: 
    T="$(mktemp -d)/trial"
mkdir -p "$T" && tar --exclude=./archive -cf - . | (cd "$T" && tar -xf -)
cd "$T" && git init -q && git add -A
git ls-files | grep -i -E '^archive/|live-check/|sealed'      # must print nothing
git grep -l -E 'SEAL-[0-9]'                                    # PUBLIC-COPY-NOTE.md, TEST-REPORT.html and the final run's record only
git cat-file -p :PASTE-INTO-CLAUDE.txt | sha256sum             # the new fingerprint
git ls-files | wc -l                                           # note the count in RELEASE-CHECKLIST.html
  8. Commit and publish. In the product folder, stage the changed files by name, commit with a message that names the version, and push. Then tag the version and, if you want a fixed download, make a GitHub release whose notes are the changelog entry: 
    git add PROJECT-INSTRUCTIONS.md PASTE-INTO-CLAUDE.txt CHANGELOG.md README.md index.html docs tests
git commit -m "v1.6: <one line on what changed>"
git push
git tag v1.6 && git push origin v1.6
gh release create v1.6 --title "Executive Decision Grill v1.6" --notes-file notes.md   # optional
  9. Check the live site. Wait until gh api repos/metamorfeus/executive-decision-grill/pages --jq .status says built. Run the two checks in section 2. Open the home page, click Copy the instructions in Chrome and in Safari or on an iPhone, paste into a text editor, and check the first and last lines. Open each guide from the home page.

4. Publish for the first time

The exact commands for the first publication are in RELEASE-CHECKLIST.html, section 4, together with the risks the owner accepts before publishing. In short:

  1. Create the local repository, stage the named files and folders, and check the file set as in step 7 above.
  2. Create the public repository with its About line, and push.
  3. Add the topics and the home page address, and switch on GitHub Pages from the root of main.
  4. Create the feedback label that the feedback form uses: gh label create feedback --description "From the feedback form" --color C5DEF5.
  5. Upload docs/social-preview.png by hand under Settings → General → Social preview. GitHub offers no command for this.
  6. Run the checks in section 2 and step 9, then mark the release checklist as published, with the date and the first commit.

5. Undo a publication

Pick the smallest step that solves the problem. Copies that others or search engines made while the repository was public cannot be recalled.

You want toDo this
Withdraw a bad version, keep the projectRevert the commit and push: git revert <commit>, then git push. Add a changelog entry that says why. If you made a GitHub release, delete it with gh release delete v1.6 --yes.
Take the home page down, keep the repositorygh api -X DELETE repos/metamorfeus/executive-decision-grill/pages
Hide the whole project for nowgh repo edit metamorfeus/executive-decision-grill --visibility private --accept-visibility-change-consequences. This also takes the Pages site down on a free account.
Delete it for goodGive gh the right first: gh auth refresh -h github.com -s delete_repo. Then gh repo delete metamorfeus/executive-decision-grill --yes. In the product folder, rm -rf .git removes only the git history; the files stay.
Before you delete anything, look at what you are about to remove, and keep the product folder as it is. It holds the only copy of the sealed scenarios, in archive/.

6. Look after feedback

  • Feedback arrives as GitHub issues through the form in .github/ISSUE_TEMPLATE/feedback.yml. The form warns people that what they write is public and asks them to remove names and confidential material.
  • If an issue still holds something confidential, act at once. Edit the text out (the edit history stays visible to people who open it), or delete the issue: gh issue delete <number> --yes. Tell the person why, in a new comment or by other means.
  • When feedback shows a real problem in Claude's behaviour, treat it like a test finding. Note it in tests/TEST-REPORT.html as a weak spot, and fix it only through a new version (section 3).
  • Do not quote feedback as praise on the pages. The pages carry no testimonials or user counts.
